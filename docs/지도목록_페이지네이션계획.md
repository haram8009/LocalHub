# 지도목록 페이지(MapView) 공공데이터 페이지네이션 전환 계획

> 선행 문서: `FE/docs/로컬전환계획.md` (tourApi.js, normalizeLocation, localStorage 게시글). 이 문서는 그중 **지도목록 페이지** 부분을 구체화한다.

## Context
현재 `MapView`의 동작:
- 지도 bounds(min/max lat·lng)를 자체 서버 `/api/locations`에 보낸다.
- **해당 영역의 전부(limit 500)**를 받아 메모리에 bounds 단위로 캐싱하고(`locationMapCache.js`), 클라이언트에서 잘라 보여준다.

관광공사 API는 이 방식과 맞지 않는다.
- bounds 조회가 없고 **중심좌표 + 반경(≤20km)** 조회만 있다.
- 결과는 `pageNo / numOfRows / totalCount` **페이지네이션**으로만 받을 수 있다.

따라서 다음을 바꾼다.
- 목록과 마커를 "현재 페이지" 단위로 표시하고, 하단에 **번호 페이저**를 둔다.
- 지도를 사용자가 움직이면 **자동 재조회**하되, **캐시로 중복 호출을 줄인다**.
- 목록이나 마커를 클릭하면 **포커스만 이동**하고 재조회하지 않는다.

## 조회 모드 (API 매핑)
| 모드 | 조건 | API | 주요 파라미터 |
|---|---|---|---|
| 초기 진입 | 지역 미선택, 첫 로드 | `areaBasedList2` | 지역 코드 없이 전국에서 선택한 contentTypeId·분류 코드로 조회, `pageNo`, `numOfRows=20`, `arrange=Q`; 결과를 목록에 표시하고 지도 bounds에 맞춤 |
| 전국 필터 | 지역 미선택, 지도 이동 전 카테고리 변경 | `areaBasedList2` | 선택한 카테고리·분류 코드로 전국을 다시 조회 |
| viewport | 지도 이동(사용자) | `locationBasedList2` | mapX/mapY=지도 중심, radius=중심→모서리 거리(m, 최대 20000), `arrange=E`(거리순), contentTypeId, pageNo, `numOfRows=20` |
| 키워드 | 검색어 있음 | `searchKeyword2` | keyword, contentTypeId, pageNo, `numOfRows=20`, `arrange=A` → 결과 페이지에 맞춰 지도 `fitLocations` |

- 카테고리 칩의 라벨은 contentTypeId로 매핑한다(관광지 12, 문화시설 14, 축제공연행사 15, 여행코스 25, 레포츠 28, 숙박 32, 쇼핑 38, 음식점 39). `전체`는 파라미터를 생략한다.
- 응답 정규화: `body.items`가 `""`(0건) 또는 단일 객체여도 항상 배열로 만든다. `totalCount`, `pageNo`, `numOfRows`를 숫자로 변환한다. `resultCode !== '0000'`이면 에러로 처리한다.
- `dist`(m, viewport 모드에만 있음)는 `distanceKm`로 변환해 목록에 "350m" 등으로 표시한다(`utils/geo.js`의 `formatDistance` 재사용).

## 캐싱 전략 (자동 재조회 + 중복 호출 억제)
1. **요청 정규화(스냅)**: 작은 이동에서 같은 캐시 키가 나오도록 요청 파라미터 자체를 양자화한다.
   - 중심좌표는 반경에 비례한 격자로 반올림한다. 격자 크기는 radius의 약 1/4이며, 위도 1° ≈ 111km로 환산한다.
   - radius는 버킷 `[500, 1000, 2000, 5000, 10000, 20000]` 중 bounds를 덮는 최소값으로 올린다.
   - **API에도 스냅된 값을 그대로 보낸다** → 캐시 키와 실제 요청이 1:1로 대응한다.
   - 약간 움직인 지도 → 같은 키 → API 호출 없이 캐시 결과를 쓰고 페이지도 유지한다.
2. **페이지 단위 캐시**: 키 = `op|contentTypeId|keyword|mapX|mapY|radius|pageNo`, 값 = `{items, totalCount, pageNo, numOfRows}`
   - 이전·다음 페이지를 왕복하거나 같은 지역으로 되돌아올 때 재호출하지 않는다.
3. **2단 저장소**: 메모리 LRU(최대 50, TTL 10분)를 쓰고, `sessionStorage`에 미러링한다. 새로고침해도 같은 탭에서는 재사용되므로 일일 호출 한도를 절약한다. sessionStorage 접근은 try/catch로 감싸고 실패하면 무시한다.
4. **in-flight 중복 제거**: 같은 키로 진행 중인 요청이 있으면 그 Promise를 공유한다. 키가 바뀌면 이전 요청을 `AbortController`로 취소한다(기존 MapView 패턴 유지).
5. **디바운스**: idle 이벤트 후 300ms 대기(기존 `LOCATION_REQUEST_DELAY` 유지).

→ 구현은 `services/locationMapCache.js`를 **키 기반 LRU+TTL 캐시로 재작성**한다. TTL과 LRU eviction 로직(`isFresh`, `touchEntry`, `evictOldestEntries`)은 재사용한다. bounds 포함 판정 함수(`containsLocationBounds` 등)는 제거한다. 스냅 함수 `snapViewportQuery(bounds)`도 이 파일에 둔다.

## 포커스 이동 시 재조회 방지
- 문제 1: `KakaoTravelMap.moveToLocation`은 `panTo` 후 kakao `idle` 이벤트를 발생시키고, 이것이 viewport-change → 재조회로 이어진다.
- 문제 2: 포커스 시 `level: 3`으로 줌인하기 때문에 radius가 바뀌어 페이지가 초기화된다.
- 수정 (`components/map/KakaoTravelMap.vue`)
  - `moveToLocation` 호출 시 `programmaticMove = true`로 표시한다. 다음 `idle`에서는 `viewport-change`를 `{ ...bounds, programmatic: true }`로 emit하고 플래그를 해제한다.
  - focusLocation watch에서는 **현재 레벨을 유지**하고 `panTo`만 한다. 현재 레벨이 7 이상(너무 넓음)일 때만 5로 줌인한다.
- 수정 (`views/MapView.vue`): `handleViewportChange`에서 `programmatic`이면 viewportBounds만 갱신하고 재조회하지 않는다.
- 키워드 모드의 `fitLocations`도 programmatic으로 처리한다(검색 결과를 viewport 재조회로 덮어쓰지 않음).

## 파일별 변경

### `services/tourApi.js` (신규, 선행 문서 2절)
`tourRequest(operation, params, {signal})` 하나와 카테고리 매핑만 둔다.

### `services/locationService.js`
- 신규 `getLocationPage({ mode, category, keyword, center, radius, areaCode, page, size, signal })`
  - mode에 따라 위 3개 API 중 하나를 호출한다.
  - 반환: `{ items: normalizedLocation[], totalCount, page, size, totalPages }`
  - 캐시 조회·저장과 in-flight 공유를 이 함수 안에서 처리한다. MapView는 캐시를 의식하지 않는다.
- 기존 `getLocations(...)`는 PostForm·home용 얇은 래퍼로 유지한다(`getLocationPage(...).items` 반환).
- `normalizeLocation`: 관광공사 필드(`contentid, title, contenttypeid, addr1, addr2, mapx, mapy, firstimage, firstimage2, dist`)를 매핑하고, 기존 반환 키는 유지한다.

### `views/MapView.vue`
- 상태 추가: `currentPage`, `totalCount`, `totalPages`, `listMode`('nationwide' | 'area' | 'viewport' | 'keyword')
- 상태 제거: `isLocationLimitReached`와 limit 안내문, `LOCATION_LIMIT`, `expandLocationBounds`/`filterLocationsByBounds` 사용부
- `loadLocations(page = 1)`
  - 검색어가 있으면 keyword 모드, 지역 선택 시 area 모드, 첫 진입 및 전국 필터에서는 area 모드(지역 코드 생략), 사용자가 지도를 움직인 뒤에는 viewport 모드(`snapViewportQuery(viewportBounds)`)로 `getLocationPage`를 호출한다.
  - 결과는 `applyLocations`로 반영한다. 선택된 항목이 현재 페이지에 없어도 마커가 유지되도록 하는 기존 로직은 그대로 둔다.
- 초기 진입(`handleMapReady`)
  - 지역 미선택이면 `areaBasedList2`로 전국의 첫 페이지를 조회해 목록에 표시하고 지도에 맞춘다.
  - 사용자가 지도를 이동하면 이후부터 viewport 모드로 조회한다.
- 재조회 시 page 처리
  - 사용자 지도 이동, 카테고리 변경, 검색 → page 1
  - 페이저 클릭 → 해당 page만 조회(지도 이동 없음, viewport 모드는 같은 스냅 키 유지)
  - 키워드 모드에서 페이지가 바뀌면 `mapComponent.fitLocations(items)`(programmatic)
- URL 쿼리에 `page`를 추가한다(`getRouteQuery`). 새로고침 시 복원하며, 기존 `query/category/placeId` 패턴을 그대로 따른다.
- `selectLocation`: 기존과 동일하게 `focusLocation`만 바꾼다. 재조회는 위 programmatic 처리로 막는다.

### `components/map/MapSidePanel.vue` → `LocationListPanel.vue`
- props 추가: `totalCount`, `currentPage`, `totalPages`, `mode`. emit 추가: `change-page`
- 헤더
  - nationwide 모드: "전국 여행지 · 총 {totalCount}개"
  - viewport 모드: "이 지역 여행지 · 총 {totalCount}개"
  - keyword 모드: "'{keyword}' 검색 결과 · 총 {totalCount}개"
  - 기존 `locations.length` 대신 totalCount를 쓴다.
- 항목에 `distanceKm`가 있으면 거리를 표시한다.
- 하단에 **번호 페이저**(‹ 이전 · 최대 5개 번호 윈도우 · 다음 ›)를 둔다.
  - 기존 `.location-list-panel__*` 스타일 토큰으로 만든다.
  - 페이지 변경 시 목록 스크롤을 맨 위로 올린다.
  - refreshing 중에는 버튼을 비활성화한다.

### `components/map/KakaoTravelMap.vue`
programmatic 플래그와 focus 줌 정책(위 절)만 수정한다. `fitLocations`, `getViewportBounds`는 재사용한다.

1. `npm run test:unit -- --run`, `npm run lint`
2. `.env`에 `VITE_TOUR_API_KEY`를 넣고 `npm run dev`를 실행한 뒤 내장 브라우저로 `/map`에서 확인한다.
   - 진입 → 서울 첫 항목으로 이동 → 주변 목록 20개와 페이저가 표시되고, 총 개수가 API의 totalCount와 일치하는지
   - 목록 클릭 → 지도만 이동하고, 네트워크 탭에 새 요청이 없는지
   - 지도를 조금 움직임 → 요청 없음(캐시 hit) / 크게 움직이거나 줌 → page 1 재조회
   - 2페이지 → 1페이지 왕복 시 두 번째부터 요청이 없는지
   - 새로고침 → sessionStorage 캐시로 즉시 표시되는지
   - 카테고리 칩, 키워드 검색(전국 결과에 맞춰 지도 fit), 필터 초기화
   - 0건 영역(바다 등)에서 빈 상태 문구가 나오는지
