# 제안 3 — 포함 검색 역색인과 Java 집합 연산 적용 기획서

## 결정과 목적

사용자가 성능 비교를 확인한 뒤 알고리즘 과제 목적을 우선하고, 정확한 단어 일치 대신 `LIKE`에 가까운 포함 검색을 요청했다. H2에 역색인을 보관하고 Java에서 집합 연산과 관련도 순위를 계산한다. 게시판은 여러 검색어의 AND 조건, 관련도 점수, 페이지를 제공한다. 검색 조건 드롭다운과 입력창 아래 도움말은 표시하지 않는다.

이번 방식은 항상 더 빠른 검색을 목적으로 선택한 것이 아니다. 아래 비교 실험에서는 포함 검색에 DB LIKE가 더 빨랐다. DB를 활용한 영속 인덱스와 Java 알고리즘을 직접 구현하고 설명할 수 있다는 교육 목적을 따른다.

## 처리 흐름

1. 문서와 검색어를 Unicode NFKC → Locale.ROOT 소문자로 정규화한다.
2. 공백·Unicode 구두점·기호를 경계로 토큰을 분리하고 중복을 제거한다. 단어를 붙이지 않는다.
3. `(term, post_id)`별 제목/본문 포함 여부를 `post_search_terms`에 저장한다.
4. 검색어 각각에 대해 `term LIKE :pattern ESCAPE '\'` 조건을 OR로 묶어 일괄 조회한다. 검색문은 바인딩하고 LIKE 메타문자는 이스케이프한다.
5. 예를 들어 ‘부산’은 사전의 ‘부산’, ‘부산에서’, ‘부산여행’을 찾는다. 매칭되는 단어의 게시글 ID를 검색어별로 합친다.
6. Java `PostingSetOperations`로 AND 교집합을 구한다. AND는 가장 작은 집합부터 처리한다. 없는 검색어는 빈 집합이다.
7. 작성자·카테고리·장소 필터를 적용한다.
8. 검색어마다 제목에 포함되면 2점, 본문에 포함되면 1점을 준다. 하나의 검색어가 여러 사전 단어에 맞아도 필드별 점수는 한 번만 준다.
9. 관련도 내림차순 → 생성일 내림차순 → ID 내림차순으로 전체 순위를 정한 뒤 페이지를 나누고 해당 글을 일괄 조회한다.

예: 제목 ‘부산 부산여행’, 본문 ‘부산에서 바다를’에서 ‘부산’을 검색하면 3점이다. ‘부산 부산’을 검색해도 3점이다. ‘부산 바다’ 검색은 두 단어가 모두 포함된 글을 반환한다.

구두점은 경계다. ‘부산,바다’에 ‘부산 바다’는 일치하지만 ‘부산바다’는 일치하지 않는다. 문장 전체 구문 검색이나 형태소 분석은 이 알고리즘의 검색 의미와 다르다.

## API와 코드

```http
GET /api/posts/search?query=부산%20바다&page=1&size=10
```

기존 `/api/posts?query=...`도 같은 검색 서비스로 연결한다. 빈 검색어 또는 기호만 있는 검색어는 최신순 목록을 반환한다. 검색은 AND로 고정하고 이전 mode 파라미터는 무시한다. 크기 1~50, 검색어 최대 100자, 정규화 후 고유 토큰 최대 10개다. 잘못된 조건은 400으로 응답한다. 일반 최신순 목록은 기존 크기 제한을 유지한다.

응답은 기존 `{ items, page, size, total, totalPages }` 형식을 유지하고 검색 항목에 정수 `relevanceScore`를 추가한다. 검색어는 URL에 보관하여 페이지 이동과 공유에 사용한다. 화면 번호는 DB ID와 별도로 1번부터 이어진다.

주요 클래스: `SearchTextNormalizer`, `PostSearchTerm`, `PostSearchIndexRepository`, `PostSearchIndexer`, `PostingSetOperations`, `PostSearchService`, `PostSearchController`, `PostQueryService`.

## 영속성과 일관성

- 최초 도입 시 기존 글을 페이지 단위로 읽어 인덱스를 구축한다. `search_index_state`에 정규화/검색 버전을 보관한다.
- 같은 버전에서는 재시작 시 인덱스를 재사용한다. 버전을 바꾸면 시작 시 트랜잭션 안에서 재구축한다.
- 등록·수정·삭제·탈퇴와 인덱스 변경을 같은 DB 트랜잭션으로 처리한다. 롤백 시 함께 되돌린다.
- `(term, post_id)` 고유 제약과 post_id 인덱스, 게시글 FK 삭제 연쇄를 사용한다.
- 조회수 증가는 코스·검색 인덱스를 다시 만들지 않는다.
- H2 REPEATABLE_READ로 동시 수정 시 인덱스와 본문이 섞이는 재현 테스트가 실패하여 검색·추천 읽기를 SERIALIZABLE로 강화했다. 같은 동시 수정 테스트로 일관성을 검증한다.

## 성능과 한계

전체 사전 행 D, 반환한 매칭 posting 수 K, 검색 토큰 Q, 최종 후보 R이면 일반적인 `%검색어%` 조회는 사전 스캔 비용이 발생한다. Java에서 부분 포함 매칭·집합 구성은 O(KQ), AND는 작은 집합 우선이며 점수 계산 O(RQ), 정렬 O(R log R)이다. 보통 B-tree의 선두 검색 이점이 줄어들기 때문에 정확한 단어 일치 역색인처럼 O(Q log D + K)라고 설명하지 않는다.

역색인 테이블은 단어 사전과 게시글 연결을 함께 보관한다. 동일 단어가 여러 게시글에 있으면 여러 행을 스캔하므로 고유 단어 개수만큼만 비용이 든다고 주장하지 않는다. 흔한 부분 문자열은 많은 posting과 메모리를 사용한다. 결과를 미리 일부만 잘라 정확도를 희생하는 제한은 두지 않았다.

## 검증

AND·부분 포함·존재하지 않는 단어·중복 검색어·NFKC·대소문자·구두점·점수 중복 방지·필터·전체 건수·순위·페이지 경계·등록/수정/삭제·롤백·초기 재구축·동시 읽기를 검증했다. H2 파일 재시작 검증과 성능 실험은 결과 보고서에 기록한다.
