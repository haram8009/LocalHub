# 부하 테스트와 병목 개선

k6로 실제 사용 비율을 흉내 낸 트래픽을 보내고 Prometheus/Grafana로 원인을 찾아, **병목을 하나씩 고치고 같은 조건으로 다시 재는** 방식으로 진행했습니다.

## 결과 요약

> 각 개선의 진단 근거, 검토한 대안, 적용 방법은 [BOTTLENECK_IMPROVEMENT.md](BOTTLENECK_IMPROVEMENT.md)에 자세히 정리했습니다.

같은 부하(초당 25요청, 2분)에서의 p95 응답 시간입니다.

| 단계 | 전체 p95 | 검색 | 주변 추천 | 글쓰기 | 실패율 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 기준선 | 1,285ms | 1,990ms | 860ms | 807ms (성공 21%) | 1.32% |
| A. 읽기 격리 수준 변경 | 772ms | 1,069ms | 818ms | 82ms | 0% |
| B+C. 검색 사전 + 주변 추천 SQL | **112ms** | **139ms** | **74ms** | 125ms | 0% |

- **처리 한계**: 약 30 req/s → **약 120 req/s** (p95 300ms 이내 유지 기준, 약 4배)
- **무중단 배포**: 초당 50요청 중 배포+롤백 → 실패 **0건**, p95 131ms, 최대 415ms (워밍업 추가 후)

## 환경과 데이터

- 로컬 Docker(서버 SSH 차단으로 로컬에서 측정). 백엔드 컨테이너 **2 CPU / 2GB**(`docker-compose.local.yml`), Hikari 커넥션 풀 10, Tomcat 스레드 200.
- 운영과 같은 구성: Caddy → 블루/그린 백엔드 → MySQL 8.
- `loadtest/seed.sql`로 만든 합성 데이터: 회원 1,000명, 게시글 **5만 건**(일부 인기 장소에 쏠리게), 코스 장소 **20만 건**, 검색 postings **약 100만 행**(서로 다른 단어 약 5.8만 개).

## 시나리오 (`loadtest/scenarios.js`)

도착률(arrival-rate) 방식이라 서버가 느려져도 요청 속도가 줄지 않습니다. 그래서 지연이 그대로 드러납니다.

| 요청 | 비율 | | 요청 | 비율 |
| --- | ---: | --- | --- | ---: |
| 목록 | 30% | | 비슷한 코스 | 10% |
| 상세 | 25% | | 관광지 | 5% |
| 검색 | 15% | | 로그인 | 3% |
| 주변 추천 | 10% | | 글쓰기 | 2% |

프로필: `smoke`(동작 확인), `load`(일정 부하), `stress`(20→300 req/s 계단), `spike`(4배 급증), `soak`(장시간).
통과 기준: 실패율 1% 미만, 전체 p95 300ms 미만(요청별 2배, 로그인 3배).

## 기준선에서 찾은 병목

스트레스 테스트에서 **약 30 req/s**에서 막혔습니다. 응답은 20초까지 늘었고 글쓰기 94%가 실패했습니다. 그런데 **CPU는 33%뿐**이었습니다.

- Hikari 풀 10개가 모두 사용 중이고 대기 188개 → Tomcat 스레드 200개가 전부 DB를 기다림. 같은 이유로 Prometheus 수집까지 끊김.
- MySQL 쿼리 시간의 **77%가 검색**의 `LIKE '%검색어%'`. 호출마다 postings 100만 행을 훑음(평균 1.5초).
- 검색·추천 읽기가 `SERIALIZABLE`이라 읽는 행마다 공유 잠금을 걸어 **교착 상태 222건**. 글쓰기가 대부분 실패.
- 주변 추천은 좌표 상자 안 장소를 전부(서울 기준 2만여 행, 본문 열 포함) 가져와 자바에서 거리 계산.

## 개선

### A. 읽기 격리 수준: SERIALIZABLE → REPEATABLE READ (스냅샷 읽기)

InnoDB의 읽기 전용 REPEATABLE READ 트랜잭션은 첫 읽기 시점 스냅샷을 **잠금 없이** 끝까지 읽습니다. 검색 결과에서 본문과 색인이 섞이지 않는다는 보장은 그대로이고, 쓰기를 막지 않습니다. 동시 수정 테스트(`PostSearchIntegrationTest`)로 "섞이지 않음 + 쓰기가 기다리지 않음"을 검증합니다.

→ 교착 상태 0, 글쓰기 p95 807ms → 82ms, 실패율 1.32% → 0%.

### B. 부분 일치 검색에 단어 사전 테이블 (Flyway V2)

부분 일치(`LIKE '%q%'`)는 인덱스를 쓸 수 없으니 **훑는 행 수를 줄였습니다.** 글마다 중복된 postings(100만 행) 대신 서로 다른 단어만 모은 `post_search_terms`(약 5.8만 행)를 훑고, 맞은 단어의 postings는 PK로 찾습니다.

→ 검색 p95 1,069ms → 139ms.

**배포하다가 발견한 문제**: 기동할 때 사전을 채우는 쿼리(행마다 `MIN` 서브쿼리를 도는 `INSERT ... SELECT`)가 100만 행에서 **9분 넘게** 걸렸습니다. 새 색이 healthy가 되지 못해 배포 스크립트가 전환을 거부했고, 기존 색은 정상 서비스를 이어 갔습니다. `GROUP BY term_hash`로 PK를 단어 수만큼만 건너뛰며 읽고(loose index scan) 잠그지 않는 SELECT 후 500개씩 넣도록 바꿔 **2.6초**가 됐습니다.

### C. 주변 추천을 DB에서 계산 (Flyway V3)

하버사인 거리와 `ROW_NUMBER() OVER (PARTITION BY post_id ...)`로 글마다 가장 가까운 장소를 고르고, 정렬과 상위 N개 자르기까지 DB에서 합니다. `(latitude, longitude, visit_order)` 덮개 인덱스로 상자 범위를 테이블에 접근하지 않고 읽고, 본문 열은 상위 N개만 읽습니다.

→ 주변 추천 p95 818ms → 74ms.

## 개선 후 스트레스 테스트

| 도착률 | 처리량 | p95 | 백엔드 CPU |
| ---: | ---: | ---: | ---: |
| 50 req/s | 50 | 112~118ms | 26~30% |
| 100 req/s | 100 | 130ms | 55% |
| 120 req/s | 120 | 190ms | 76% |
| 135 req/s 이상 | 120~160 | 1.4~3.0초 | **97~100%** |

이제 막히는 곳은 **백엔드 CPU(2코어)**입니다. 동시에 풀 10개도 가득 찹니다. DB 잠금 대기는 사라졌고, 실패 없이 느려지기만 합니다. 시간을 가장 많이 쓰는 요청은 목록·검색(`/api/posts`)과 상세입니다.

다음 후보(측정 전):
- 목록의 `COUNT(*)`와 OFFSET 페이지네이션 → 키셋 페이지네이션
- 검색 결과 메타데이터 조회(`IN` 목록 최대 1.3만 개)
- JDBC `useLocalSessionState=true`로 트랜잭션마다 도는 `SELECT @@session.transaction_read_only` 왕복 제거
- 백엔드 CPU·풀 크기 조정(서버 사양에 맞춰)

## 부하 중 블루그린 배포 (초당 50요청, 배포 후 롤백)

| | 워밍업 없음 | 워밍업 20초 |
| --- | ---: | ---: |
| 실패 | 2건 / 11,786 | **0건 / 12,021** |
| p95 / p99 | 5,326ms / 6,783ms | **131ms / 208ms** |
| 최대 | 12.5초 | **415ms** |
| 처리하지 못한 요청(dropped) | 234 | **0** |

**원인**: 새로 뜬 JVM은 JIT 컴파일 전이라 느립니다. 헬스체크와 스모크 테스트는 요청 몇 개뿐이라 데워지지 않은 채 트래픽을 받았고, 전환 직후 20초 동안 CPU 100%에 p95가 4~9초였습니다. 롤백도 같습니다(정지했던 색을 다시 띄움).

**해결**: `deploy.sh`와 `rollback.sh`가 전환하기 전에 새 색에 읽기 요청을 20초 동안 보냅니다(`WARMUP_SECONDS`, `deploy/lib.sh`의 `warm_up`). 배포는 48초에서 68초로 늘었습니다.

## 직접 실행하기

```bash
# 0) 로컬 스택 실행 (docs/DEPLOYMENT.md "로컬에서 먼저 검증" 참고, COMPOSE_PROFILES=monitoring 포함)
# 1) 부하 데이터 넣기 (localhost 전용, 검색 색인 재구축에 수 분)
bash loadtest/seed.sh
# 2) 실행. 결과 요약은 loadtest/results/<프로필>-<시각>.json
bash loadtest/run.sh smoke
RATE=25 DURATION=2m bash loadtest/run.sh load
bash loadtest/run.sh stress
```

Grafana(`http://localhost:3000`)의 EnjoyTrip 대시보드에서 k6 지표(요청 수, p95, 실패율)와 백엔드·DB 지표를 같은 시간축으로 봅니다.

**디스크 주의**: 이미지를 빌드할 때마다 빌드 캐시가 수 GB씩 쌓입니다. 측정 중 C: 드라이브가 꽉 차서 Docker가 읽기 전용이 되었고, 그때 빌드한 이미지의 jar가 깨져 배포가 거부됐습니다. 빌드 직후 `docker builder prune -af`로 비우세요. 서버는 `deploy.sh`가 옛 앱 이미지를 정리합니다.
