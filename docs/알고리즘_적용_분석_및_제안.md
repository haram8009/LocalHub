## 1. 변경된 전략

알고리즘 계산과 데이터 관리는 Spring Boot 서버에서 담당한다. Vue는 검색 조건을 보내고 추천·검색 결과를 표시한다. 게시글과 코스의 원본은 H2에 저장한다.

| 기능 | 서버에서 직접 구현할 알고리즘 | Vue 역할 |
| --- | --- | --- |
| 제안 2: 비슷한 여행 코스 찾기 | Jaccard 유사도 + LCS 동적 계획법 | 게시글 상세에서 추천 목록·이유 표시 |
| 제안 3: 여러 단어로 게시글 검색 | 역색인 + 집합 교집합·합집합 + 관련도 점수 | 검색어·AND/OR 조건 입력, 결과·페이지 표시 |

추천과 검색을 각각 독립된 기능으로 구현하고 기획서도 각각 작성한다. 구현된 알고리즘의 입력·출력과 비교 실험을 분리해 설명할 수 있다.

### 현재 코드와 전환 지점

- [posts.js](frontend/src/services/posts.js): 현재 localStorage CRUD, includes 검색, 방문 순서 정규화를 담당한다. 게시글 CRUD·조회·검색을 서버 API 호출로 전환한다.
- [PostForm.vue](frontend/src/components/post/PostForm.vue): 관광지 선택과 수동 순서 편집 UI를 활용한다. 서버에는 관광지 ID와 방문 순서를 전송한다.
- [PostDetailView.vue](frontend/src/views/PostDetailView.vue): 유사 코스 추천 API를 호출하고 추천 카드를 추가한다.
- [PostListView.vue](frontend/src/views/PostListView.vue): 서버 검색 결과와 전체 건수·페이지 정보를 표시한다.
- [home.js](frontend/src/services/home.js): 현재 주변 여행 코스 조회는 이번 유사 코스 추천과 목적이 다르다. 추천의 첫 적용 화면은 게시글 상세로 정한다.

서버 신규 구축 시 게시글 쓰기에 필요한 사용자 식별·작성자 검증도 서버에서 처리한다. 브라우저 목업 세션이나 요청의 authorId를 그대로 신뢰하는 방식으로 옮기지 않는다.

## 2. 공통 데이터 모델과 서버 구성

### 제안 테이블 — 프런트엔드 필드 대조 후 보완

DB에 저장할 원본 필드와 화면 응답 DTO를 구분한다. 화면에 필요한 필드가 모두 DB 컬럼일 필요는 없지만, 서버 응답 또는 프런트 어댑터에서 해당 값을 제공해야 한다.

| 테이블 | 주요 필드 | 역할 |
| --- | --- | --- |
| member | id, login_id, name, email, password_hash VARCHAR(255), status, created_at | 내부 회원 키와 로그인 아이디 구분. 인증 설계는 별도 구현 |
| post | id, author_id, author_name_snapshot, category, title, content, view_count, created_at, updated_at, version | 게시글 원본·작성 당시 이름·조회수·동시 수정 버전 |
| place | id, source, content_id, content_type_id, name, address, latitude, longitude, thumbnail_image_url, original_image_url, cached_at | 관광지 외부 식별자와 코스 표시용 캐시 |
| post_place | post_id, place_id, visit_order | 코스의 방문 장소와 순서 |
| post_search_term | term, post_id, title_hit, body_hit | 게시글 검색용 역색인 |

#### content_id만으로 상세 조회가 가능한가?

현재 [getLocation()](frontend/src/services/locationService.js)은 관광공사 detailCommon2에 contentId만 전달해 기본 상세를 조회한다. 여기서 얻은 contentTypeId까지 사용하면 전체 상세 조회 흐름을 이어갈 수 있다. 단, 이는 관광공사에 존재하는 실제 ID여야 한다.

| 현재 상세 호출 | 식별에 사용하는 값 |
| --- | --- |
| detailCommon2 | contentId |
| detailImage2 | contentId. 현재 코드는 imageYN도 전달 |
| detailIntro2 | contentId + contentTypeId |
| detailInfo2 | contentId + contentTypeId |

따라서 content_id만 저장하는 최소 모델도 기본 상세 조회의 출발점으로 사용할 수 있다. 권장 모델은 content_id와 content_type_id를 함께 저장해 상세 요청에 재사용한다. 서비스 인증키 등 공통 요청 설정은 별도로 필요하다.

name·address·좌표·이미지는 상세 조회를 위한 필수 키가 아니다. 코스 목록과 지도에서 장소마다 외부 API를 다시 호출하지 않도록 보관하는 표시용 캐시다. 상세 소개·시설·이용시간·전체 사진 목록은 필요 시 외부 API에서 조회하고 캐시할 수 있으므로, 모두 정규 DB 컬럼으로 만들 필요는 없다. 이름·주소만으로 상세 조회를 대체하지 않는다.

#### 식별자 및 관계

- place.id는 서버 내부 PK다. 관광공사 content_id와 구분한다.
- (source, content_id)를 고유하게 관리한다. 초기 source는 TOUR_API로 한정한다.
- Vue의 location.contentId와 location.id에는 현재 계약에 맞게 외부 content_id 문자열을 반환한다. 내부 PK는 필요할 때 별도 placeId 필드로 제공한다.
- 추천 알고리즘은 내부 place.id 배열을 비교한다. 같은 외부 관광지는 하나의 내부 place로 연결되어야 한다.
- post.author_id는 member.id를 참조한다. 현재 Vue의 authStore.user.id는 로그인 아이디 문자열이므로 DB PK를 그대로 대입하지 않는다.
- 호환 DTO에서 user.id와 post.authorId는 같은 login_id 문자열을 사용하고, 작성 권한은 서버의 인증 주체와 내부 FK로 판정한다.
- post_place의 (post_id, visit_order), (post_id, place_id)를 고유하게 관리한다. 현재 폼의 중복 관광지 선택 방지와 대응한다.
- (place_id, post_id)에 인덱스를 두어 공통 장소 후보와 장소별 관련 글을 조회한다.
- post_search_term의 (term, post_id)를 기본 키로 두고 post_id에 보조 인덱스를 둔다.
- 게시글 삭제 시 post_place와 post_search_term도 삭제하되 공유 관광지 place는 함께 삭제하지 않는다.

#### 화면 응답 DTO

게시글 목록·검색은 최소한 id, category, categoryLabel, title, authorId, authorName, viewCount, createdAt, updatedAt, locationCount를 제공한다. 홈에서 사용하는 요약을 위해 content 또는 summary도 제공한다. 상세·수정 응답은 content와 visitOrder 순의 locations를 포함한다. 검색 응답 항목의 식별자도 postId가 아닌 기존 화면의 id로 통일한다.

- category: COURSE / REVIEW / TIP / RECOMMENDATION. categoryLabel은 서버 코드 매핑으로 파생한다.
- authorName: 현재 로컬 저장 방식과 맞추려면 작성 시 이름을 author_name_snapshot에 저장한다. 프로필 변경 시 자동 변경하지 않는 정책이다.
- locationCount: post_place 개수로 계산한다. 별도 컬럼은 초기에는 두지 않는다.
- viewCount: 현재 getPost 호출은 조회수를 증가시킨다. 서버에서는 동시 조회 증가분을 잃지 않는 갱신 방식으로 처리한다. 조회수 변경이 코스·검색 인덱스 재생성을 유발하지 않게 분리한다.
- createdAt/updatedAt: 시간대가 포함된 ISO 8601 문자열로 응답한다.

locations 항목은 현재 normalizeLocationResponse와 호환되도록 id, contentId, contentTypeId, name, category, categoryLabel, contentType, address, region, latitude, longitude, thumbnailImageUrl, originalImageUrl, visitOrder를 제공한다. description·tel은 상세 응답에서 보충하거나 빈 문자열로 처리할 수 있다. category는 contentTypeId에서, region은 주소에서 파생 가능하다. distanceKm는 기준 위치에 따라 달라지는 값이므로 관광지 고정 컬럼에 저장하지 않는다. 서버는 좌표 누락을 null로 전달하고 프런트 어댑터가 기존 유효 좌표 검사에 맞게 정규화한다.

place는 최신 표시용 캐시이며 게시글 작성 당시 장소 정보의 영구 스냅샷은 아니다. 현재 로컬 방식의 ‘작성 당시 장소명·주소·이미지 보존’까지 유지해야 한다면 post_place에 필요한 스냅샷 필드를 추가해야 한다. 초기 서버 전략은 최신 캐시를 사용하는 것으로 명시한다.

#### 기존 기능 유지 시 필요한 정책

- 마이페이지는 authorId 필터를 사용한다. 내 글 API는 인증 주체로 조회하고, 일반 작성자 필터가 필요하면 외부 login_id를 내부 키로 변환한다.
- 장소별 관련 글은 현재 contentId뿐 아니라 이름·주소·좌표 기반 대체 매칭도 한다. 서버의 정확한 FK 조회만으로는 기존 동작 전체를 대체하지 못한다. 프런트 서비스에서 기존 placeId 쿼리를 외부 content_id로 해석하고, 기존 matchesPlace 규칙이 필요한 요청은 별도 매칭 로직으로 처리한다. 매칭 후보를 찾았다는 이유만으로 DB 관광지를 병합하지 않는다.
- 현재 마이페이지는 회원 탈퇴 후 게시글 유지를 안내한다. 초기 서버에서는 회원을 비활성 상태로 관리하고 게시글을 연쇄 삭제하지 않는다. 탈퇴 사용자의 응답 authorId는 null로 처리하고 작성자 표시는 ‘탈퇴한 사용자’로 대체한다. 실제 개인정보 정리 정책은 회원 기능 설계에서 확정한다.
- HomeView의 작성자 표시 함수는 현재 authorName을 읽지 않는다. 서버 DTO를 camelCase로 통일할 때 이 함수도 authorName을 읽도록 수정해야 한다.
- 추천·검색의 글 공개 범위 필터는 향후 비공개 기능을 도입할 때 적용한다. 현재 게시글 모델에는 공개 범위 필드가 없으므로 초기 글은 공개 게시글로 정의한다.

실제 API ID와 demo-* 샘플 ID를 같은 장소로 자동 간주하지 않는다. 실제 관광지 ID로 정리한 서버 시드 데이터를 준비한다. 새 게시글의 외부 관광지 ID는 서버가 확인하고 내부 place로 연결하며, 클라이언트가 전달한 표시 정보를 검증 없이 원본으로 저장하지 않는다. 브라우저별 기존 글의 자동 이전은 별도 범위로 둔다.

### H2 저장·실행 전략

- 개발·시연 서버: 파일 모드 jdbc:h2:file:./data/localhub를 사용한다. 상대 경로는 서버 실행 디렉터리 기준이므로 배포 시 저장 경로를 고정한다.
- 자동 테스트: MySQL 서버에 실행별로 격리된 enjoytrip_test_... DB를 생성하여 통합 테스트를 수행하고, 종료 시 삭제한다. 서비스 DB는 사용하지 않는다.
- 파일 모드는 동일 DB 파일과 스키마가 유지되어야 재시작 후 게시글·회원·역색인이 남는다. 인메모리 모드는 JVM 종료 시 사라지며 DB_CLOSE_DELAY=-1도 프로세스 재시작까지 보존하지 않는다. [H2 공식 문서](https://h2database.com/html/features.html)
- 기본 배포는 Spring Boot 단일 프로세스의 임베디드 H2로 한다. 여러 서버 프로세스가 같은 임베디드 DB 파일을 직접 공유하는 구조로 확장하지 않는다.
- 초기 스키마는 버전 관리 SQL로 생성한다. JPA를 선택하면 파일 DB의 ddl-auto는 validate로 두고 시작 전 마이그레이션을 적용한다. 파일 DB에서 create/create-drop으로 매번 재생성하지 않는다.
- H2 기본 문법을 기준으로 BIGINT GENERATED BY DEFAULT AS IDENTITY, VARCHAR, CLOB, BOOLEAN 등으로 DDL을 작성한다. FK·고유 제약·역색인 테이블 구조는 앞선 논리 모델을 유지한다.
- 검색어 정규화·점수 계산은 Java에서 수행한다. DB 고유 전문 검색 기능에 의존하지 않는다.
- H2 데이터 파일은 저장소에 커밋하지 않는다. H2 Console은 필요한 로컬 개발 프로필에서만 활성화한다.
- 동시 수정과 검색 읽기 일관성은 선택한 H2 트랜잭션 격리 수준에서 통합 테스트한다. 읽기 전용 선언만으로 일관된 스냅샷이 보장된다고 가정하지 않는다.

### 서버 책임 분리

아래는 신규 서버에 만들 구조의 예시이며 현재 존재하는 파일은 아니다.

~~~text
post/
  PostController.java
  PostService.java
  PostRepository.java
  PostPlaceRepository.java
recommendation/
  CourseRecommendationController.java
  CourseRecommendationService.java
  CourseSimilarityCalculator.java
search/
  PostSearchController.java
  PostSearchService.java
  PostSearchIndexer.java
  SearchTextNormalizer.java
  PostingSetOperations.java
  PostSearchTermRepository.java
~~~

- Controller: 요청 검증과 DTO 변환.
- Service: 데이터 조회, 알고리즘 실행, 정렬·페이지 구성.
- Calculator/SetOperations: DB·HTTP와 독립된 순수 Java 알고리즘.
- Repository: DB 저장·조회. JPA 또는 MyBatis 선택에 따라 구현한다.

**초기 버전은 DB에 역색인을 저장한다.** 서버 메모리에만 인덱스를 두는 방식은 재시작 복구와 서버 간 동기화가 필요하므로 초기 필수 범위에서 제외한다. DB는 검색어별 게시글 ID 목록을 찾고, Java는 그 목록의 집합 연산과 점수 계산을 담당한다.

## 3. 제안 2 — Jaccard + LCS 기반 유사 코스 추천

### 문제 정의와 서비스

게시글 상세에서 현재 코스와 장소 구성 및 방문 순서가 비슷한 다른 코스를 추천한다. 사용자의 장기 취향을 학습하는 개인화 추천이 아니라 **현재 보고 있는 코스 기준의 콘텐츠 유사도 추천**이다.

~~~text
기준 코스: A → B → C → D
후보 1:   A → B → E → D
후보 2:   D → C → B → A
~~~

후보 2는 같은 장소를 방문하지만 순서가 반대다. 장소 집합 비교와 순서 비교를 함께 사용해 차이를 반영한다.

### 서버 처리 흐름

1. 기준 게시글과 visit_order 순으로 정렬한 관광지 ID 목록을 조회한다.
2. post_place에서 기준 관광지 중 하나 이상을 포함한 다른 게시글 ID를 조회한다.
3. 후보의 관광지 목록을 일괄 조회하고 게시글별로 묶는다. 후보마다 DB를 호출하는 N+1 조회를 피한다.
4. HashSet으로 교집합·합집합 크기를 계산한다.
5. 두 ID 배열의 LCS 길이를 DP로 계산한다.
6. 점수를 합산하여 정렬하고 상위 limit개를 반환한다.
7. Vue에서 ‘공통 관광지 3곳 · 같은 방문 순서 3곳’ 등의 이유를 표시한다.

기준 게시글, 빈 코스, 접근 권한이 없는 게시글은 제외한다. 공통 장소가 없는 코스는 두 점수가 모두 0이므로 초기 정책에서는 추천하지 않는다. 추천이 없으면 빈 목록을 반환한다.

### 점수 정의

~~~text
Jaccard = 공통 관광지 수 / 두 코스의 전체 고유 관광지 수
순서 유사도 = LCS 길이 / max(기준 코스 길이, 후보 코스 길이)
최종 점수 = 0.6 × Jaccard + 0.4 × 순서 유사도
~~~

예시 점수:

- 후보 1: Jaccard = 3/5, LCS = 3/4 → 최종 0.66.
- 후보 2: Jaccard = 4/4, LCS = 1/4 → 최종 0.70.

이 가중치에서는 장소 구성이 같은 역순 코스가 더 높을 수 있다. 이는 오류가 아니라 장소 겹침을 우선한 정책이다. 순서가 비슷한 코스를 더 우선하려면 가중치를 조정하고 동일한 예제로 기대 동작을 검증한다. 가중치는 초기 제안값이며 품질 검증 없이 최적이라고 단정하지 않는다.

동점은 created_at 내림차순, post_id 내림차순으로 처리해 결과를 안정적으로 만든다. 점수는 반올림 전 값으로 정렬하고 표시할 때만 반올림한다.

### LCS 구현 방향

~~~text
장소 ID가 같으면:
  dp[i][j] = dp[i - 1][j - 1] + 1
다르면:
  dp[i][j] = max(dp[i - 1][j], dp[i][j - 1])
~~~

초기 응답은 LCS 길이만 제공하므로 2행 배열을 사용하는 공간 최적화가 가능하다. 실제 공통 방문 순서까지 표시하려면 수열 복원 기능을 별도로 추가한다.

### API 제안

아래 JSON은 알고리즘 결과를 설명하기 위한 축약 예시다. 실제 항목에는 공통 게시글 DTO의 표시 필드도 포함한다.

~~~http
GET /api/posts/{postId}/similar?limit=3
~~~

~~~json
{
  "items": [
    {
      "id": 42,
      "title": "서울 궁궐 산책 코스",
      "score": 0.66,
      "commonPlaceCount": 3,
      "lcsLength": 3,
      "placeSimilarity": 0.6,
      "orderSimilarity": 0.75
    }
  ]
}
~~~

limit의 기본값은 3, 최대값은 10으로 제안한다. 기준 게시글이 없으면 404, 잘못된 limit이면 400을 반환한다. 숫자 제한은 구현 시 확정할 서비스 정책이다.

### 복잡도와 확장

- 두 코스 길이가 M, N이면 Jaccard는 해시 집합 기준 기대 O(M + N).
- LCS 시간 O(MN), 길이 계산 공간 O(min(M, N)).
- 후보 P개, 최대 코스 길이 L이면 LCS 계산 전체 O(P × L²).
- 전체 후보 정렬 O(P log P). DB 조회와 응답 생성 비용은 별도이다.

초기에는 공통 장소가 있는 모든 후보에 점수를 계산한다. Jaccard 상위 일부에만 LCS를 적용하면 최종 점수 상위 코스를 놓칠 수 있다. 데이터가 커져 후보 제한을 추가할 경우 근사 추천으로 구분하고 누락률을 평가한다.

### 검증

- 동일·역순·부분 일치·불일치·빈 코스의 점수와 순서 검증.
- 샘플 ID와 실제 관광지 ID 정합성 검증.
- 자기 게시글 제외, 동점 정렬, 삭제·수정 직후 결과 반영 확인.
- 작은 배열에서 별도 단순 구현과 LCS 길이 비교.
- 후보 수와 코스 길이별 계산 시간, DB 쿼리 수, API 전체 응답 시간 측정.

## 4. 제안 3 — 역색인과 집합 연산 기반 게시글 검색

### 문제 정의와 서비스

기존 includes 검색은 검색 문자열 전체가 연속으로 등장해야 한다. 서버에서 검색어별 게시글 목록을 관리하고, 여러 검색어를 모두 포함하거나 하나 이상 포함하는 검색을 제공한다.

~~~text
부산 → {1, 4, 8}
바다 → {1, 3, 8}

AND → {1, 8}
OR  → {1, 3, 4, 8}
~~~

### 초기 검색 의미

첫 구현은 **정규화된 단어의 정확한 일치**로 범위를 정한다.

- 문서와 검색어 모두 Unicode NFKC 정규화 및 Locale.ROOT 소문자 변환.
- 공백·구두점을 경계로 토큰 분리. 구두점을 제거해 두 단어를 합치지 않는다.
- 빈 토큰을 버리고 중복 검색어를 제거한다.
- 제목과 본문에 같은 정규화 규칙을 적용한다.

‘부산 바다’는 ‘부산 여행, 바다 산책’에 일치한다. 그러나 ‘부산에서 바다를’에는 초기 단어 일치 정책상 일치하지 않는다. 형태소 분석이나 부분 문자열 검색은 별도 확장이다. 기존 includes와 검색 의미가 다르다는 점을 UI 안내와 테스트에 반영한다.

### DB 역색인 구성

~~~text
term | post_id | title_hit | body_hit
부산 | 1       | true      | true
바다 | 1       | false     | true
부산 | 4       | true      | false
~~~

같은 게시글에서 단어가 여러 번 나와도 (term, post_id) 행은 하나다. 초기 점수는 단어 출현 횟수 대신 제목·본문 포함 여부를 사용한다.

### Java 검색 처리 흐름

1. 검색어를 정규화하고 토큰 목록을 만든다.
2. DB에서 해당 토큰들의 post_search_term 행을 묶어서 조회한다.
3. Java의 Map<String, Set<Long>>에 검색어별 게시글 ID 집합을 구성한다.
4. AND는 가장 작은 집합부터 교집합을 구한다. OR는 집합을 합친다.
5. 존재하지 않는 토큰은 빈 집합으로 취급한다. AND 결과는 즉시 빈 목록이고, OR는 다른 토큰 결과를 유지한다.
6. 후보의 카테고리·접근 범위를 필터링한 뒤 점수를 계산한다.
7. 관련도 내림차순 → 작성일 내림차순 → ID 내림차순으로 정렬한다.
8. 정렬된 전체 결과에서 페이지를 자르고 표시 데이터를 조회한다. ID로 DB 재조회한 결과도 계산된 순서를 유지해 반환한다.

~~~text
관련도 점수 = 검색어별 (제목 포함 시 2점 + 본문 포함 시 1점)의 합
~~~

예를 들어 검색어 2개가 제목·본문 양쪽에 모두 있으면 6점이다. 중복 검색어는 한 번만 계산한다. 관련도는 0~1 유사도가 아닌 정수 점수이며, 이름을 relevanceScore로 구분한다.

검색 후보를 DB에서 먼저 한 페이지로 제한하면 전체 검색 결과의 올바른 순위와 total을 구할 수 없으므로, 필터링·점수 계산·정렬 후 페이지를 나눈다.

### 작성·수정·삭제와 일관성

PostService의 게시글 저장과 PostSearchIndexer의 역색인 변경을 **동일 DB 트랜잭션**으로 처리한다.

- 작성: 게시글 저장 → 제목·본문 분석 → 검색 행 일괄 삽입.
- 수정: 동일 게시글의 이전 검색 행 삭제 → 최신 텍스트로 재생성.
- 삭제: 검색 행·코스 연결 정보·게시글 삭제.
- 실패: 게시글과 검색 행을 함께 롤백.

동일 게시글의 동시 수정은 낙관적 잠금 또는 행 잠금 정책으로 제어한다. 검색 중 서로 다른 버전의 본문과 인덱스를 섞지 않도록 검색의 다단계 DB 조회에도 일관된 읽기 트랜잭션 정책을 적용한다.

역색인은 H2 파일 DB에 저장하므로 동일 파일을 유지하고 스키마를 재생성하지 않으면 서버 재시작 후에도 유지된다. 테스트용 인메모리 DB에는 이 보존 조건이 적용되지 않는다. 기존 글 도입 시 최초 일괄 구축이 필요하고, 정규화 규칙 변경 시 재구축한다. 초기 재구축은 점검 시간에 수행하고, 재구축 중인 일부 인덱스를 정상 결과로 제공하지 않는다.

### API 제안

아래 JSON은 축약 예시이며 실제 items는 위 공통 게시글 목록 DTO에 relevanceScore를 추가한다.

~~~http
GET /api/posts/search?query=부산%20바다&mode=AND&page=1&size=10
~~~

~~~json
{
  "items": [
    {
      "id": 1,
      "title": "부산 바다 여행",
      "relevanceScore": 6
    }
  ],
  "page": 1,
  "size": 10,
  "total": 1,
  "totalPages": 1
}
~~~

- 외부 API의 page는 기존 화면에 맞춰 1부터 시작한다. 서버 내부 페이지 도구가 0부터 시작하면 경계에서 변환한다.
- 기본 mode는 AND, size는 10으로 제안한다.
- size 최대 50, 검색어 최대 100자, 고유 토큰 최대 10개를 초기 제한으로 제안한다.
- 검색어가 공백이거나 정규화 후 토큰이 없으면 일반 최신순 목록 조회로 처리한다.
- 잘못된 mode·페이지·크기 등은 400으로 응답한다.
- category 필터를 지원할 경우 전체 건수 계산과 페이지 분할 전에 적용한다.

### 복잡도와 확장

전체 텍스트 길이 T, 검색 토큰 수 Q, 각 토큰의 게시글 목록 크기 dᵢ, 최종 후보 수 R로 둔다.

- 단순 토큰 추출 O(T). DB 저장·인덱스 유지 비용은 별도이다.
- 집합 구성 및 OR 연산은 기대 O(Σdᵢ).
- AND는 가장 작은 집합 크기를 d_min이라 하면 해시 조회 기준 기대 O(Q × d_min). 단, DB에서 목록을 읽고 집합을 구성하는 O(Σdᵢ) 비용은 별도로 발생한다.
- 집합 메모리 O(Σdᵢ), 후보 점수 계산은 단순 구현 O(RQ).
- 최종 정렬 O(R log R).

작은·중간 규모의 과제에서는 DB 역색인과 Java 집합 연산으로 동작 원리를 설명하기 쉽다. 흔한 단어로 후보가 많아지면 DB 전송량과 Java 메모리 비용을 측정하고, 필요할 때 DB 집계·Top-K 등으로 확장한다.

### 검증

- AND·OR·존재하지 않는 단어·중복 검색어·빈 검색어 검증.
- 제목 가중치와 동점 정렬, 페이지 경계·전체 건수 검증.
- 작성·수정·삭제 및 롤백 후 검색 결과 확인.
- 서버 재시작 후 동일 결과 확인.
- 동일한 정규화·단어 일치 규칙을 쓰는 전체 순회 구현과 결과 비교.
- 인덱스 구축·갱신 시간, DB 저장 크기, 조회 행 수, Java 메모리, API 응답 시간을 각각 측정.

기존 includes와 다른 검색 의미를 가진 결과를 그대로 비교해 성능 개선이라고 주장하지 않는다.

## 5. 비밀번호 해싱 전략

### 적용 범위와 현재 코드

초기 목업에서는 브라우저에서 SHA-256을 한 번 계산한 비밀번호를 localStorage에 저장·비교했다. 현재는 Spring Security PasswordEncoder 기반 서버 저장·검증으로 전환했으며, 사용하지 않는 목업 암호화 유틸리티는 제거했다.

추천·검색 알고리즘 두 기능은 그대로 유지하며, 비밀번호 해싱은 회원 기능의 별도 적용 항목으로 추가한다. 직접 해시 함수를 구현하는 대신 검증된 라이브러리를 사용한다.

### 선택: Argon2id

Argon2id를 초기 기본값으로 선택한다. 초기 비용은 메모리 19 MiB(19,456 KiB), 반복 2회, 병렬도 1로 설정하고 서버에서 동시 로그인 부하와 지연을 측정해 조정한다. 이는 OWASP가 제시한 최소 구성 중 하나이며, 성능 검증이 완료된 프로젝트 설정이라는 뜻은 아니다. [OWASP Password Storage Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)

- Salt: 라이브러리가 encode 호출마다 무작위로 생성하도록 한다. 사용자 ID나 공통 상수를 Salt로 쓰지 않는다.
- 저장: 알고리즘·비용·Salt·해시가 포함된 인코딩 문자열 전체를 member.password_hash VARCHAR(255)에 보관한다. Salt 별도 컬럼은 필요하지 않다.
- Pepper: 초기 필수 범위에는 포함하지 않는다. 도입 시 DB와 분리된 비밀 관리 및 교체 전략을 함께 설계한다.
- DB가 H2인 것과 회원 비밀번호 해싱 알고리즘은 별개다. H2 접속 계정의 비밀번호와 서비스 회원의 password_hash를 구분한다.

### 키 스트레칭 적용 방법

키 스트레칭(Key Stretching)은 비밀번호 계산 비용을 높여 공격자의 반복 추측을 어렵게 하는 기법이다. Argon2id는 내부 반복 연산과 메모리 비용을 제공하므로 라이브러리 설정으로 적용한다. 별도 반복문으로 encode를 여러 번 호출하거나 SHA-256을 덧붙이지 않는다.

| 설정 | 초기 제안값 | 의미 |
| --- | --- | --- |
| iterations | 2 | 내부 연산 반복 횟수. 증가하면 계산 시간이 늘어남 |
| memory | 19,456 KiB (19 MiB) | 해싱에 사용하는 메모리 비용. 동시 인증 요청 수와 함께 검토 |
| parallelism | 1 | 계산을 나누는 병렬 처리 정도. 높을수록 무조건 안전해지는 수치는 아님 |
| saltLength | 16바이트 | 매 encode 호출에서 생성하는 무작위 Salt 길이 |
| hashLength | 32바이트 | 결과 해시 길이. 반복 횟수나 메모리 비용과 구분 |

iterations=2는 SHA-256을 두 번 호출한다는 뜻이 아니라 Argon2id 내부의 메모리를 사용하는 연산을 반복하는 설정이다. 초기 비용은 [OWASP 권장 최소 구성](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)을 출발점으로 삼고 실제 서버 측정 결과에 따라 조정한다.

Salt는 같은 비밀번호의 저장값을 다르게 만들어 사전 계산 재사용을 어렵게 한다. 키 스트레칭과 메모리 비용은 개별 비밀번호의 추측 비용을 높인다. HTTPS는 전송 구간을 보호한다.

### 책임 분담과 처리 순서

~~~text
Vue: 비밀번호 입력 및 형식 검사
  → HTTPS로 서버 전송 (전송 구간 암호화)
Spring Boot: 원문 비밀번호를 받아 서버 입력 검증
  → PasswordEncoder.encode() 한 번 호출
Argon2id: 무작위 Salt + 설정한 반복 연산·메모리 비용 적용
  → H2의 member.password_hash에 인코딩 문자열 저장
~~~

Spring Security는 인증·접근 제어를 담당하며 등록한 PasswordEncoder를 통해 비밀번호를 검증한다. 회원가입 서비스는 같은 인코더의 encode를 호출해 저장한다. 로그인에서는 matches가 저장된 Salt와 비용 설정을 사용하므로 애플리케이션이 수동으로 반복 계산하거나 Salt를 재생성하지 않는다.

### 비용 설정 검증 및 발표 문구

- 동일 서버에서 초기값과 반복 횟수·메모리 비용을 높인 후보 설정을 비교한다.
- 해싱·검증 각각의 처리 시간과 동시 요청 시 메모리 사용량을 측정한다.
- JVM 워밍업 후 반복 측정하고 단일 요청 시간과 동시 로그인 지연을 구분한다.
- 비밀번호 검증 정확성을 확인하고 사용자 대기 시간과 서버 자원 한도 안에서 비용을 결정한다.
- 설정 변경 시 기존 인코더를 검증용으로 유지하고 로그인 성공 후 재해싱 정책으로 갱신한다.

제안서에는 다음처럼 계획을 기술한다.

> Spring Security의 PasswordEncoder에 Argon2id를 연결하고, 반복 횟수와 메모리 비용을 설정하여 키 스트레칭을 적용한다. 비밀번호마다 무작위 Salt를 생성하며, 동시 로그인 부하를 측정해 서버 자원과 응답 시간을 고려한 비용을 결정한다.

실제 구현·검증 완료 후에는 완료형으로 바꾸고 설정값과 측정 결과를 함께 제시한다. 현재 문서는 설계 단계이므로 구현 완료로 표현하지 않는다.

### Spring Boot 연결 예시

아래는 Argon2PasswordEncoder와 DelegatingPasswordEncoder를 이용하는 설계 예시다. 실제 서버의 Spring Boot·Spring Security 버전 확정 후 의존성과 API를 확인하여 적용한다. 해당 Argon2 구현에는 BouncyCastle이 필요하다. [Spring Security 비밀번호 저장 문서](https://docs.spring.io/spring-security/reference/7.0/features/authentication/password-storage.html)

~~~java
@Bean
PasswordEncoder passwordEncoder() {
    PasswordEncoder argon2 = new Argon2PasswordEncoder(
        16,     // salt length (bytes)
        32,     // hash length (bytes)
        1,      // parallelism
        19456,  // memory (KiB)
        2       // iterations
    );
    return new DelegatingPasswordEncoder(
        "argon2id-v1", Map.of("argon2id-v1", argon2)
    );
}
~~~

이 예시는 java.util.Map, Spring의 Bean, Spring Security의 PasswordEncoder·DelegatingPasswordEncoder·Argon2PasswordEncoder import가 필요하다. 저장값에는 {argon2id-v1} 접두사가 붙으며 뒤에 Argon2 인코딩 문자열이 이어진다. 접두사는 이 프로젝트의 인코더 등록 키다. [Argon2PasswordEncoder 생성자 명세](https://docs.spring.io/spring-security/reference/7.0/api/java/org/springframework/security/crypto/argon2/Argon2PasswordEncoder.html)

### 가입·로그인·변경 흐름

1. 회원가입: Vue가 HTTPS 요청 본문으로 비밀번호를 전송한다. 서버가 정책을 검증하고 encode(rawPassword) 결과만 저장한다.
2. 로그인: login_id로 회원을 찾고 matches(rawPassword, storedHash)로 검증한다. encode 결과 문자열끼리 비교하지 않는다. Salt 때문에 같은 비밀번호도 다른 저장값이 생성될 수 있다.
3. 비밀번호 변경: 인증된 사용자의 현재 비밀번호를 matches로 확인한 뒤 새 비밀번호를 encode하여 저장한다.
4. 비밀번호 재설정: 유효기간·일회성 조건을 갖춘 서버 발급 재설정 토큰으로 본인 확인을 완료한 후 새 비밀번호를 해싱한다. 현재 목업의 아이디·이메일 일치만으로 재설정을 허용하는 흐름을 서버에 그대로 옮기지 않는다.
5. 회원 탈퇴 확인: 현재 비밀번호도 같은 matches 검증을 재사용한다.

프런트 auth.js는 서버 API 호출로 바꾸고 crypto.js의 SHA-256 사전 해싱을 인증 흐름에서 제거한다. 비밀번호를 trim하거나 Unicode 정규화하지 않는다. 요청 DTO에는 비밀번호를 받을 수 있지만, 응답 DTO·로그·브라우저 저장소에는 원문과 password_hash 모두 포함하지 않는다.

### 기존 데이터와 설정 변경

- 로컬 SHA-256 저장값은 원래 비밀번호로 복원하거나 Argon2id 해시로 자동 변환할 수 없다. 새 서버는 새 가입·서버 시드 계정으로 시작한다. 기존 계정 이관이 필요하면 본인 확인 후 비밀번호 재설정으로 처리한다.
- 클라이언트의 기존 SHA-256 값을 새 비밀번호처럼 서버가 받아 저장하는 방식은 채택하지 않는다.
- 비용 정책을 바꿀 때 argon2id-v2 같은 새 등록 키를 추가하고, 기존 인코더도 검증용으로 유지한다. 로그인 성공 시 upgradeEncoding 판정 또는 정책 버전 비교를 통해 입력받은 원문으로 새 해시를 저장한다.
- 해시 비용은 공격 비용을 높이는 목적이다. 단순 SHA-256보다 빠른지를 개선 지표로 사용하지 않는다.

### 검증 항목

- 동일 비밀번호를 두 번 encode했을 때 저장 문자열은 다르고 matches는 둘 다 성공하는지 확인.
- 틀린 비밀번호·손상된 저장값·지원하지 않는 접두사 처리가 성공으로 이어지지 않는지 확인.
- 회원가입, 로그인, 비밀번호 변경·재설정·탈퇴 확인의 서버 통합 테스트.
- 새 비밀번호 저장 후 이전 비밀번호가 실패하는지 확인.
- H2 파일 DB 재시작 후에도 로그인 가능한지 확인.
- 응답 DTO·로그·프런트 저장소에 비밀번호·해시가 노출되지 않는지 확인.
- 순차·동시 요청의 해싱 지연과 메모리를 측정하여 비용·요청 제한 정책 결정.
