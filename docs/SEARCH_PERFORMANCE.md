# 제안 3 검색 성능 평가

## 결론과 선택

‘역색인’도 DB SELECT를 사용한다. 핵심 차이는 텍스트를 DB가 검색/정렬할지, 역색인 posting을 가져와 Java가 집합/순위를 계산할지다.

정확한 단어 일치 역색인은 드문 단어에 이점이 있을 수 있다. 하지만 사용자가 요청한 **단어 사전의 부분 포함 검색**에서는 이번 데이터상 DB LIKE가 더 빨랐다. 단순한 소규모 서비스라면 DB 검색이 유지보수와 성능 측면에서 적합하다. 사용자의 최종 선택은 **알고리즘 과제 목적의 DB 영속 역색인 + Java 집합 연산 + 포함 검색**이다.

## 공정 비교 조건

- JDK 21, H2 2.3.232 인메모리 DB. 실제 회원·게시글 DB에는 접속하지 않는다.
- 고정 난수 20261015, 게시글 100 / 1,000 / 10,000개, 제목 4개·본문 16개의 200종 단어와 공통 단어를 생성한다.
- 게시글과 역색인은 같은 정규화된 단어로 구성한다. `%검색어%`와 사전 단어 부분 포함은 같은 결과 의미를 가진다.
- 세 방식 모두 제목 2점/본문 1점의 중복 없는 점수와 ID 내림차순 동점 정렬을 적용한다. 생성일은 모두 같다고 가정한다.
- DB LIKE, 역색인+Java, 역색인+DB GROUP BY의 **전체 결과 ID 및 점수 순서가 일치하는지** 먼저 확인한다.
- 각각 8회 워밍업, 21회 측정의 중앙값. H2 결과 캐시 비활성화.
- 전체 결과 ID·관련도 계산·정렬을 포함한다. HTTP, JPA 엔티티 직렬화, 파일 I/O, 인덱스 구축/갱신 비용, 실제 장소 필터는 제외한다. 페이지 단위 SELECT/LIMIT의 추가 이점도 측정하지 않는다.
- 단일 JVM의 순차 미세 실험이며 여러 JVM fork/JMH 및 운영 부하 측정은 아니다. 짧은 시간은 JIT·GC·측정 순서에 민감하다.

## 포함 검색 측정 (ms)

| 글 수 | 검색어 | 조건 | 매칭 글 | DB LIKE | 역색인+Java | 역색인+DB 집계 |
|---:|---|---|---:|---:|---:|---:|
| 100 | 단어3 + 단어147 | AND | 6 | 0.632 | 0.949 | 1.532 |
| 1,000 | 단어3 + 단어147 | AND | 57 | 0.414 | 3.766 | 5.304 |
| 10,000 | 단어3 + 단어147 | AND | 612 | 3.269 | 19.696 | 33.249 |
| 10,000 | 단어3 + 단어147 | OR | 7,088 | 6.591 | 20.786 | 30.850 |
| 10,000 | 여행 + 코스 | AND | 5,000 | 2.428 | 20.931 | 33.067 |
| 10,000 | 여행 + 코스 | OR | 10,000 | 4.126 | 19.574 | 31.338 |

`단어3`은 `단어30`, `단어31` 등에도 포함되어 정확 일치 때의 드문 단어가 더 이상 드물지 않게 된다. CSV의 rare 라벨은 초기 정확 일치 실험의 검색어 그룹 이름이며 부분 검색의 희소성을 뜻하지 않는다.

초기 정확 일치 예비 실험에서는 같은 1만 건의 ‘단어3 + 단어147’ OR가 LIKE 약 5.43ms, 역색인+Java 약 1.44ms였다. **검색 의미를 바꾼 뒤에도 그 이점이 유지된다고 주장하면 안 된다.** 해당 예비 측정 원자료는 `search-comparison-exact.csv`이며 이후 포함 검색 구현이 우선된다.

## 해석과 확장

포함 검색의 선두 `%`는 term 인덱스의 일반적인 선두 범위 탐색 이점을 줄인다. 사전 posting 행 수가 게시글 수보다 많고, 전송 후 Java에서 다시 매칭·중복 제거·집합 구성·정렬을 수행하므로 비용이 커질 수 있다. ‘DB 대신 Java여서 빠르다’ 또는 ‘역색인이면 항상 빠르다’는 결론을 내리지 않는다.

데이터가 커지면 고유 단어 사전과 posting 분리, n-gram 후보 인덱스, 전문 검색 등을 비교할 수 있다. 현재는 구현 원리를 설명하기 쉬운 알고리즘 과제 범위를 유지한다.

## 재현

소스: `docs/benchmarks/SearchComparison.java`

```powershell
# H2 2.3.232 JAR의 실제 경로를 지정
java -cp '경로/h2-2.3.232.jar' docs/benchmarks/SearchComparison.java --contains
```

이 소스는 비교용 임시 메모리 DB만 생성하며 서비스 검색 코드나 운영 DB에 적용되는 기능이 아니다. `--contains`가 없으면 예비 정확 일치 실험을 재현한다. 원자료: `docs/benchmarks/search-comparison-contains.csv`.

참고: [H2 SELECT](https://h2database.com/html/commands.html#select), [H2 트랜잭션 격리 수준](https://h2database.com/html/advanced.html#transaction_isolation).
